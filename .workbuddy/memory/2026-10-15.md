### 「2D 小程序」路线评估（结论）
**不是无脑更快，是「UI 和后端快一半、动效和美术慢一半」。**

小程序/小游戏侧确凿优势（已查证）：
- **语音识别**：微信同声传译插件（AppID `wx069ba97219f66d99`），免费 **1000 次/天**，个人主体可用，半天接完。
  Unity 侧要接 iOS Speech / Android SpeechRecognizer 两套端侧 SDK + 权限 + 降级，是 TRN-01~05 最大的坑。
- **UI 12 个页面**：WXML/WXSS 远快于 Unity uGUI + TextMeshPro
- **存档/账号**：`wx.setStorageSync` 或微信云开发（免后端），顺手解决 PRD §10 第 7 条
- **分发**：扫码即预览，无 Unity build（几分钟）/签名流程；iOS 不用过 Xcode
- **多指手势**：小程序 touch 事件直接给 `touches.length`，开发者工具可模拟；Unity 侧强制真机

小程序/小游戏侧劣势：
- **2D 动画美术是要害**：3D 靠骨骼复用白得 idle/walk/run 三件套；2D 每个动作要序列帧或 Spine/DragonBones。
  PRD 要求约 10 套动作 × 12~24 帧 = 120~240 张图。
- **移动层必须重写**：PetController 的转向/避障/边界钳制要换成 x 轴 + 翻转 + y-sort
- **表现层全部归零**：3D 模型 / Animator / 材质 / URP 全废
- **观感落差**：展板是写实渲染，2D 更难糊弄；需求文档 §10-3 自己已提示过落差风险

### ⚠️ 合规硬门槛（关键，必须前置决策）
- 养成 + 等级 + 金币 + 商店 + 训练 **极可能被微信判为「游戏」**。历史上微信对「养宝宝/养成/积分升级」类小程序
  直接驳回并回复「请注册一个新账号，同时选择游戏类目」（来源：微信服务市场审核记录 2019）。
- **一旦选游戏类目，类目不可再改**（微信运营规范 3.4）。小程序 ↔ 小游戏 两条路不可回头。
- 小游戏上线资质：**软著 + 工信部备案 + 自审自查报告 + 隐私协议**。
  **只有涉及虚拟支付（内购/充值）才需要版号**；纯广告变现不需要版号。
  个人主体**无法开通虚拟支付**。
- → **PRD「V1 不接真实支付」这一条不只是产品决定，是资质决定，必须守住。**
- 包体：小程序主包 ≤2MB / 总 ≤30MB；小游戏首包 ≤4MB / 分包合计 ≤30MB；
  资源上 CDN 需 ICP 备案的 https 域名。

### 三条可选路线（待用户拍板）
- **A**：Unity 3D 原型保留不动；另起小程序工程，把架构用 TS 重写，表现换 2D。省设计成本，付编码 + 美术成本。**(我推荐)**
- **B**：小程序 + 静态立绘 + 代码 Tween 动效。美术成本≈0，一周能出可玩闭环，但生命感弱，验证不了 PRD 的核心命题。
- **C**：Unity 直接导微信小游戏（WXSDK 转换）。保住 C# 代码，但要过首包 4MB / 资源全 CDN / iOS 不允许动态下载代码 / URP WebGL 兼容等一堆坑。**不推荐作为第一步。**

### 用户已答复（2026-10-15）
1. **第一步目标可以是「验证技术架构」**
2. **2D 美术先用 AI 生成**，省成本
3. **主体是企业**（非个体），**最终产品肯定需要虚拟支付**

### 答复带来的方案变更（重要）
- **「2D 小程序」这个前提不成立**：要虚拟支付 → 必须游戏类目 → 只能是**微信小游戏**，不是普通小程序。
  两者技术栈完全不同：小程序 = WXML/WXSS/DOM，主包 2MB；小游戏 = **只有 Canvas，没有 DOM**，首包 4MB。
  → 上一轮「UI 用 WXML/WXSS 写最快」这条优势**作废**，小游戏 UI 必须用引擎画。
- **语音方案降级**：微信同声传译插件是**小程序插件，小游戏不可用**。
  小游戏只能 `wx.getRecorderManager` 录音 → 上传云端 ASR（腾讯云/百度/讯飞）→ 需云函数转发（API Key 不能放前端）。
  → 从「半天接完 + 免费 1000 次/天」变成「多一层后端 + 按量计费」。这是对我上一轮判断的修正。
- **版号是长周期硬门槛**：企业主体申请，须通过**有出版资质的单位**提交，周期 **4–6 个月**，且不确定性高。
  软著约 60 天，工信部备案数个工作日至数周。**资质线必须现在启动，与开发并行**，否则总周期 = 开发 + 4~6 个月。
- 「免版号」路径只对**纯广告变现（IAA）**开放，且个人主体口径更明确；
  **企业主体做纯 IAA 是否免版号，各来源说法不一致 → 必须找微信官方或代理确认，不能凭印象定**。
- 企业主体才可开通虚拟支付；个人主体连升级路径都没有，必须重注册。

### 关键待定决策（技术栈二选一，目标冲突）
- 要「2D + AI 低成本美术」→ **Cocos Creator 2D + TypeScript**（小游戏生态最好、2D 动画/图集自带、包体小），
  但 Unity 的 24 文件 / 5037 行架构要全部翻译。
- 要「架构零重写」→ **Unity 直接转微信小游戏（WXSDK）**，但仍是 3D（现有资源就是 3D 低模），
  且要过 4MB 首包 / 资源全上 CDN（域名需 ICP 备案）/ iOS 不允许动态下载代码 / URP WebGL 兼容等坑。
- 两个目标互斥，需用户拍板。还需确认：**最终产品是只有微信小游戏，还是同时要独立 APP（iOS/Android）**——
  若要两端通吃，Unity 是唯一一次开发出两端的选项。

### AI 生成 2D 美术的可行做法（已给建议）
- **不要用 AI 生成序列帧**（角色跨帧漂移：花纹/体型/颜色变化），这是最常见的坑。
- 推荐：AI 生成**单张标准姿势立绘**（透明底）→ 切分部位 → Spine/DragonBones 绑骨骼 → 动作由骨骼驱动。
  只需 1 张图 + 骨骼动画，成本最低。
- 更省：单张立绘 + 程序化形变（缩放/倾斜/位移/呼吸曲线），动作只做 2~3 个（Idle/Eat/Happy）。
- 场景背景 AI 生成 4 张（家中/花园/公园/夜晚），成本接近零。
- 一致性手段：ControlNet / IP-Adapter / LoRA 固定角色。
- **版权风险**：① 训练数据来源不明，国内已有相关侵权判例；② 软著与版号申请要提交美术资源，
  审核方可能要求权属说明。建议保留生成记录 + 做足人工改造使其具备独创性。

## 第二轮答复后的定调（21:31）

用户答复：**「App 首先需要」**；判据是「小游戏开发快就先做小游戏，比 APP 麻烦就直接做 APP，完善目前的版本」。

### 结论：两端都用同一套 Unity 工程出，顺序上先小游戏
- **开发工作量：APP 更少**——继续在现有 Unity 工程上写就行；小游戏要多一套转换工程（净增）。
- **上线时间：小游戏快得多**——APP 的资质清单长出一大截。
- 真正阻塞上线的是**资质不是开发**，所以建议开发只做一遍，先上小游戏。

### 关键证据一：APP 资质比小游戏重得多（多源一致）
游戏类 APP 上架国内安卓商店 + 苹果中国区，需要：
**APP 备案 + 软著 + 文网文 + ICP 许可证 + ISBN 版号 + 游戏备案 + 各商店独立企业实名 + 安全检测报告 + 防沉迷接入**
- 周期：软著 5–15 天（加急）~30 工作日；APP 备案 7–20 工作日；**文网文 20–40 工作日**；
  **ICP 许可证 40–80 工作日**；版号 4–6 个月（另有来源说 6–12 个月）。
- 安卓要**华为 / 小米 / OPPO / vivo / 应用宝 各自注册+认证+提交一轮**；苹果中国区游戏必须版号 + 企业账号。
- 微信小游戏只需：**软著 + 微信备案 + 版号（虚拟支付时）**，一个口，审核 13–37 工作日。
→ **不对称点：小游戏不需要 ICP 许可证和文网文，APP 需要。**

### 关键证据二：小游戏首包实测（已量）
- `Assets/ithappy/Animals_FREE/Skyboxes/Skybox_Textures/Skybox_5.png` = **4.61 MB**，**单张就超过小游戏首包 4MB 上限** → 必须外置 CDN
- 狗的资产：`Dog_001.fbx` 0.78MB + 共享 `Textures/Texture.png` 0.77MB + 三个动画(idle 0.32/walk 0.29/run 0.28) ≈ **2.4MB（未压缩）**
- 加上 Unity wasm（brotli 约 2MB+）→ 首包极紧，必须重度裁剪 + 资源全外置
- 另需：ICP 备案的 https CDN 域名、iOS 不允许动态下载代码的平台分支
→ 小游戏转换是**净增工作量**，不是零成本。
- 附带：整包 7 只动物 5.7MB，只用狗 → 其余 6 只应排除出构建，别留在 Resources。

### 2D 这条线可以收了
既然 APP 首先需要 + 走 Unity + 完善现有 3D 工程 → **2D 不再是选项**（Unity 做 2D 无收益，AI 2D 立绘用不上）。
AI 生成美术剩下的有效用途：**UI 图标、场景背景、商店商品图**（AI 擅长、成本近零）。

### 硬门槛：iOS 打包需要 Mac
用户环境是 Windows。iOS 必须 macOS + Xcode。**需确认用户是否有 Mac / 云 Mac / 租构建机**，否则 iOS 出不来。

### 待确认（不能凭印象定）
- **同一个版号能否覆盖「微信小游戏版」和「APP 版」两个平台版本？** 不确定，须向出版单位确认，
  **不要按「一次搞定」规划**。

### 建议的语音统一方案
APP 端侧 SDK（iOS Speech + Android SpeechRecognizer 两套）vs 小游戏（录音 + 云函数 + 第三方 ASR）。
**建议统一走第三方云 ASR**，两端共用一份后端，省一套代码。

## 微信小游戏适配性核查（23:25，实测工程）

用户问「Unity 能直接导出微信小游戏吗？只做一套 Unity 就行？」

### 官方工具链确认存在
微信官方提供 **Unity 转换插件 + 平台能力 C# SDK（WX_SDK）**，可把 Unity 工程导出为小游戏包。
官方评估页：`developers.weixin.qq.com/minigame/dev/guide/game-engine/unity-webgl-transform/Design/Evaluation.html`

### 官方「不支持 / 需调整」清单（原文）
| 能力 | 官方结论 |
| --- | --- |
| 渲染接口 | **仅 WebGL 1.0（≈ OpenGL ES 2.0）正式支持，2.0 处于 Beta** |
| 渲染管线 | 支持标准管线、URP |
| 多线程 | **不支持**，要删 |
| 网络 | **不支持 System.Net**；HTTP 必须 UnityWebRequest，TCP 走 WX SDK 或 WebSocket |
| 文件 API | **不支持 System.File**；原文「**玩家存档请使用服务器或云开发**」 |
| 音频 | 支持 Unity Audio / FMOD，**不支持 Wwise** |
| Lua | 不支持 LuaJIT |
| 存储 | 200MB，可申请到 1GB |

### 实测本工程（`Assets/Scripts` 24 文件 + ProjectSettings + manifest）
**✅ 干净项（没踩雷）**
- 运行时无 `System.IO`（只在 `Editor/PetAnimationBuilder.cs`、`Editor/PetSceneBuilder.cs`，不进包）
- 无 `System.Net` / 多线程 / `PlayerPrefs` / `Application.persistentDataPath` / `UnityWebRequest`
- 无 `Resources` 目录；代码没用 NavMesh，也没用 Addressables

**⚠️ 要处理的 4 项**
1. **颜色空间是 Linear**（`m_ActiveColorSpace: 1`）—— 官方 FAQ：Linear 需要 WebGL 2.0 才支持，是已知坑
2. **URP 17.6.0 在用**（挂 QualitySettings 两个质量级：PC_RPAsset + Mobile_RPAsset）——
   官方说 URP 支持但 WebGL2 相关特性是 Beta；社区案例：URP 后处理在小游戏上花屏 / 场景叠加
3. **`Packages/manifest.json` 是 URP 模板默认清单**，装了用不到的重包：
   `ai.inference 2.6.1`、`ai.assistant 2.20.0-pre.2`、`ai.navigation 2.0.14`、`visualscripting 1.9.12`、
   `timeline 6.6.0`、`postprocessing 3.5.4`(PPv2)、`test-framework 1.8.0`，
   以及 terrain / vehicles / cloth / xr / video / particlesystem / tilemap 等模块 → **4MB 首包下必须裁**
4. **首包体积**：`Skybox_5.png` 4.61MB 单张即超限；狗资产约 2.4MB 未压缩 → 必须外置 CDN

### ⚠️ 最关键的不确定项：Unity 版本
官方评估页写的支持范围是 **Unity 2018~2022 + 团结引擎 3**，并写明「**以团结引擎为主要支持目标**」。
本工程是 **Unity 6000.6.4f1（Unity 6.6）→ 不在明确列表内**。
官方当前推的是**团结引擎**（Unity 中国分支，基于 2022 LTS）。
→ **必须先确认 Unity 6.6 能否转换；否则要迁到团结引擎（又是一笔迁移成本）。不可按「能转」规划。**

### 另一未装项
`Library/PlayerDataCache` 为空 → **从未构建过任何平台，Unity WebGL Build Support 模块也没装**。
要真验证必须先装 WebGL 模块 + 转换插件 + 一个测试用 AppID。

### 结论口径
「一套 Unity 工程」成立，但准确说是：**一套业务逻辑 + 一层平台适配 + 一次资源/工程改造**。
业务逻辑层（PetController / PetBehaviorController / PetEmotion / PetStateMachine / GestureRecognizer /
PetAnimationMap）两端共用；额外要做的是输入、存档、音频、网络、文件路径的适配 + 首包裁剪 + CDN。

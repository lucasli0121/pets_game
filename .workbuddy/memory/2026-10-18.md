### 工具踩坑（editor_sdk）
- `doc_insert_markdown` 对较长或含复杂结构的 chunk 会报 `HTML segment insertion failed`（单段落、单表、单个标题都正常）
- `create_doc` 返回的是**纯文本**，file_id 要用正则 `file_id=([\w\-]+)` 提取，不是 JSON
- `last_edit_index` 不等于文档末尾；追加必须每次重新调 `doc_get_last_operable_pos` 取 position
- 可靠做法：按段落/表格切块（≤300 字），逐块插在末尾位置；失败则按行降级重试，再失败用 `doc_insert_text` 兜底
- `doc_resolve_document_structure` + `doc_get_table_info` 的单元格文本字段是 `text`（table_info）/ `text_preview`（structure），且 structure 的 cell 预览被截到 ~10 字，读全表要走 `doc_get_table_info`

### 3. 广告改为双类型（已落）
| 类型 | API | 触发 | 发奖 | 频控 |
| --- | --- | --- | --- | --- |
| 开屏插屏 | `wx.createInterstitialAd` | 每次冷启动 | 否 | 每日次数 + 最小间隔，后台配 |
| 激励视频 | `wx.createRewardedVideoAd` | 积分不足时 | 是（服务端校验） | 每日上限 |

**微信官方限制（已核实）**：
- 插屏**全局只创建一次**，重复创建会 **memory leak**（官方文档明确提示）
- 插屏有**平台频控**：「每个用户每天可观看广告的次数有限」，`show()` 可能直接 reject，必须 catch 且不能阻塞启动
- 用户可主动关闭（即"可跳过"）

另：用户可用后台调 `config_food.price` / `config_scene.price` 提高消耗，让激励视频自然出现，无需新机制。

### 建议（已提出，用户已采纳）
开屏广告不要每次冷启动都弹：建议每日 1–2 次上限 + **首次安装不弹**，否则新用户第一印象就是广告，会掉首日留存。

**已落文档（14:03）**：
- PRD §1.3：开屏插屏「每日上限默认 1–2 次，首次安装当天不展示，两项均后台配置」
- 后台 §13.8：配置项 `skip_first_day`、`daily_limit`、`min_interval_sec`，三者全部后台可配不写死

## pets_server 后端 + 管理端交付完成（23:15）

按 `docs/电子宠物APP_V1_后台与管理端需求文档.docx` + `UI与功能需求文档.docx` 实现。

### 关键技术决策（对后续所有后端工作有效）
1. **standalone Mongo 无多文档事务，这是数据模型的硬约束**。mongo 192.168.1.63 是单机非副本集，
   `startSession` 事务直接不可用。做法：把 integrally-coupled 的「积分余额 + 库存 + 场景」合并成
   `user_assets` 单文档（聚合根），扣款把余额条件写进 filter：
   `{_id:uid, "points.balance":{$gte:cost}}` + `$inc`。失败方向只可能是「不扣也不加」。
2. 幂等 = `request_dedup(user_id, request_id)` 唯一索引 + 30 天 TTL；**业务失败不写 dedup，允许修正后重试**。
3. 自实现 HS256 JWT（`crypto/hmac` + ConstantTimeCompare），不引入第三方 jwt 库。
4. 管理端零依赖 SPA（app.js 38KB）+ `go:embed`，单 exe 部署，无 node 构建链。
5. 等级曲线服务端只读 `config_level` 表逐级扣减，绝不写死公式。

### 验收状态
- 15 个用例全绿（`go test ./... -count=1` → `ok pets_server/test 15.359s`）
- gofmt 无输出、go vet 无输出、`node --check app.js` OK
- 二进制 `bin/pets-server.exe` 16.7MB，单文件含管理端静态资源
- 15 个客户端接口 + 17 个管理端接口 + 10 个管理页面

### 两处需产品决策的问题（已写进 README，未擅自改文档数值）
1. **「48 小时不登录状态不空」用文档数值达不到**：饱腹 −10/h → 10 小时归零；
   快乐 −5/h → 20 小时归零；24h 离线上限永远来不及生效。
   当前如实执行（归零即 0、不为负、宠物不死亡、经验不丢）。
2. **等级表 9 行数字无法用单一 ×1.5 复现**：507×1.5=760.5 应为 760 但文档写 761；
   761×1.5=1141.5 应为 1142 但文档写 1141。处理：默认值逐字锁定文档原表，
   管理端「按 ×1.5 重新生成」按钮用标准四舍五入。

### 测试性能坑（重要，可复用）
每个测试用例固定 12 秒。逐层测量：Connect 2ms / Ping 51ms / Drop 5ms，但 `store.Open` 9s。
根因是 **Mongo 建集合时首次 `CreateMany` 索引要 300–800ms 且服务端串行**，
18 个集合 = 9 秒。试过 8 路并发建索引 → 反而更慢（单个涨到 3.7s），证明串行在服务端。
**解法：共用测试库 `pets_test_shared` + 每个用例只 purge 数据不清集合**，索引只建一次。
效果：首用例 9.9s，其余 0.7–1.6s，全量 25s → 复跑 15.3s。

## 三条产品决策落地（23:55）

### ① 状态下限改为 1，不归零
原先按 [0,100] 夹取，饱腹 −10/h 离线 10 小时就归零，快乐 −5/h 20 小时归零，
「48 小时不登录状态不空」这条验收永远达不到。产品决策：**下限 1**。
- `domain.MinStateValue = 1`；`Settle` 改用 `clampRange(v, 1, 100)`
- 新增 `ClampState`（夹 [1,100]），喂养 / 互动的加值路径都改走它
  —— 否则数值为 0 的历史记录会因「加 0 还是 0」卡在下限之下
- `Clamp`（[0,max]）保留给积分这类可以归零的字段
- `Test08` 断言改为 satiety/happiness 都 ≥ 1
- 真机验证：把 last_settle_at 推到 48h 前、状态设 80 → sync-state 返回 `satiety=1 happiness=1`

### ② 等级表纯配置，删掉 ×1.5 生成
用户要求「所有值都在后台配置、不计算」。注意：文档 13.8 ① 第 466 行其实**要求过**
「提供按 ×1.5 重新生成按钮」，但也同时要求「服务端只读表不写死公式」。按用户决策取消按钮。
- 删除 `domain.GenerateLevels`、`POST /api/admin/config/generate-levels`、管理端「重新生成」按钮
- `DefaultLevels` 改为 untyped 硬编码数组，**scale 也列出，不再用 `1+(lv-1)*0.06` 计算**
- 管理端新增一级：expRequired=0、scale=1，必须手填；0 值输入框用 `.input-bad` 标红 + 顶部 banner 提示
- 保存草稿与发布都走 `ValidateSnapshot`，所以 0 值在**保存草稿时**就被拦（文案已改准）
- 实测校验：`L9 的升级经验必须大于 0`、`L3 的升级经验必须大于 L2`

### ③ 单管理员模型
只保留 admin 一个账号，不做多账号 / 改密页面。
默认账号密码改为 **admin / admin**（`ADMIN_INIT_PASSWORD`），上线必须覆盖。
改密唯一方式：改 env → 清空 `admin_users` → 重启（种子只在集合为空时执行）。
RBAC 三角色矩阵代码保留未删，将来要多账号不用改中间件。

### 数据修复（重要）
库里 `config_level.scale` 存着旧版计算出的浮点脏值 `1.3599999999999999`。
种子只在 `config_meta` 为空时跑，所以新默认值不会覆盖已有数据 —— **清 config_level 反而会把等级表搞空**。
正确做法：`UpdateMany` 用 `$round: ["$scale", 2]` 就地修，并清掉可能带旧值的 `config_draft`。

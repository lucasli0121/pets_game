# 2026-10-19

## 修掉「Game 视图背景全黑」——正交相机 + 俯角把远处背景推出画面

用户在 Play 模式下截图：背景整片黑，只剩狗和假阴影。

### 排查过程
Edit 模式下量到的数据全部「正常」，所以第一轮判断错了方向：
```
背景 quad 2.1375 x 3.8 m，z=40，材质 URP/Unlit，贴图 scene_home_day 1080x1920
far=50，相机到背景中心距离 43.2m —— 全部没被裁
```
连 `cam.Render()` 类的验证都做不了（URP 下必失败，见 MEMORY 第 15d 条），
SceneView 四视角截图里狗也只有一个小点（SceneView 用自己的透视相机）。

### 真因：正交投影 + 俯角 ≠ 平行投影
进 Play 模式用 `WorldToViewportPoint` 量背景**四角**，而不是中心：
```
corner worldY=-1.90 -> viewport y = -2.259     ← 画面外
corner worldY=+1.90 -> viewport y = -1.281     ← 画面外
```
背景整体落在画面下方 1.3~2.3 倍屏高处。

**推导**：正交相机的视线互相平行，但相机的**朝向**仍由 transform 决定。
背景摆在世界固定 z=40，相机在 z=-3.2 且俯角 12°，
画面纵向偏移 = 距离 × tan(俯角) = 43.2 × tan(12°) ≈ **9.2m**，
而可视高只有 3.8m —— 背景必然掉出画面。
狗不受影响是因为它只在 3.2m 处，偏移仅 0.68m。

**上一轮我为什么量错**：量的是背景中心点 `b.center.y = 0`，
而背景实际范围是 y ∈ [-1.9, +1.9]。中心点碰巧落在画面附近，
四角全在画面外。**验背景必须量四角（或 min/max），不能量中心。**

### 修法：背景挂成相机的子物体
```csharp
go.transform.SetParent(cam.transform, false);
go.transform.localPosition = new Vector3(0f, 0f, BackgroundDistance); // 8f
go.transform.localRotation = Quaternion.identity;  // 相机看向自身 +Z，不用转 180°
```
局部坐标下背景永远正对取景平面，偏移恒为零，
改 `orthographicSize` / `cameraPitch` 都自动跟随。

配套改动：
- `BackgroundDistance` 40f → **8f**。挂子物体后 d 只决定深度排序，
  唯一约束是 d > cameraDistance(3.2m) 否则狗会盖在背景前
- `farClipPlane` 从 `BackgroundDistance + 10f`(50m) 降到 **+2f**(10m)，
  那个长远裁剪面是「背景摆世界远处」时代的遗留
- `CreateBackgroundQuad(lib)` → `CreateBackgroundQuad(lib, cam)`，
  不再内部 `FindAnyObjectByType<Camera>()`（MEMORY 第 10c 条：找场景对象可以，
  但传参更可靠，且构建顺序上相机必须先建好）
- 背景尺寸的 aspect **写死 9/16**，不用 `cam.aspect`。
  构建时 Game 窗口常是 16:9，用实时 aspect 会算出 16:9 的背景尺寸，
  之后切竖屏又对不上。背景尺寸只该跟图自身比例 + 可视高有关。

### 验证结果
```
Edit:   bg viewport x 0.342..0.658  y 0.0216..0.9784（16:9 未裁切时）
        深度 dog=3.21 < bg=7.73   ok=True
Play:   cam rect=(0.34, 0, 0.32, 1) aspect=0.5625
        bg viewport x 0..1   y 0.0216..0.9784   ← 完整铺满裁切区
        bg tex = scene_home_day
        dog viewport=(0.826, 0.413)  ← x 偏移是自主行走，纵向仍稳在地面线
```

### 顺带记录
- Play 模式下 `PetPortraitViewport` 才生效（Edit 模式 Update 不跑），
  `cam.rect` 从 (0,0,1,1) 变成 (0.34,0,0.32,1)，即居中 9:16 裁切
- 退出 Play 时 `PetDebugPanel.DrawStatus` 抛 NRE（PetDebugPanel.cs:132），
  引用随场景销毁失效，与本次改动无关，但这个面板迟早要换成正式 UI
- 重建场景前必须确认已退出 Play：
  `EditorSceneManager.NewScene` 在 Play 下抛
  `InvalidOperationException: This cannot be used during play mode`

## 第二轮：「背景还是黑的」—— quad 背面剔除

上一轮修完俯角偏移，用户反馈背景仍然黑。**真因是另一个独立问题**。

### 为什么坐标数字完全正常
```
bg viewport x 0..1   y 0.0216..0.9784   ← 四角铺满，几何完全正确
bg depth 7.73 < far 10                  ← 没被远裁剪面切掉
材质 URP/Unlit，贴图 scene_home_day     ← 都在
```
**背面剔除发生在光栅化阶段**，`WorldToViewportPoint` 只做几何变换，
量出来永远是对的。几何对、材质对、深度对，只有「这一面朝不朝相机」错了。
所以这类问题**从坐标数字上算不出来**。

### 真因
`BuildQuadMesh` 的三角形绕序是 `0,1,2 / 0,2,3`，法线给的是 `Vector3.back`（-Z），
所以 quad **正面朝本地 -Z**。
背景挂在相机局部 +Z 处（相机看向自身 +Z），不转的话相机看到的是背面 → 被剔除 → 全黑。

上一轮我把 `localRotation` 改成 `Quaternion.identity` 并注释写
「相机看向自身 +Z，不需要额外旋转」—— **这句是错的**，
当时只验证了坐标没验证朝向。

修法：`localRotation = Quaternion.Euler(0f, 180f, 0f)`

### 教训：这两个 bug 症状一模一样（背景全黑）
① 背景摆世界远处 → 俯角把它推出画面
② 背景正面背对相机 → 背面剔除
**排查时必须分开验**：
- 位置问题 → 量四角 viewport
- 朝向问题 → 查 mesh 法线与视线方向的点积
只做前者会漏掉后者，且会误以为「已经修好了」。

### 新增构建时自检 `VerifyBackgroundFacingCamera`
挂在 `CreateBackgroundQuad` 末尾，每次构建自动跑：
```csharp
Vector3 worldNormal = mr.transform.TransformDirection(normals[0]).normalized;
Vector3 toBg = (mr.bounds.center - cam.transform.position).normalized;
float dot = Vector3.Dot(worldNormal, toBg);
if (dot <= 0f) Debug.LogError(...);   // 背面朝向，会被剔除
```
顺带校验四角是否落在 viewport 内（覆盖俯角偏移那类问题）。
实测 `dot = 1`，自检通过。

### 小坑
`MeshRenderer` **没有** `sharedMesh`，那是 `MeshFilter` 的成员 → CS1061×2。
法线要写 `mr.GetComponent<MeshFilter>().sharedMesh.normals`。

## 第三轮：宠物悬空 + 与沙发重叠（都不是模型的问题）

### 悬空：groundLine 是凭感觉设的，从没对着背景图校准
`groundLine = 0.42` 是上一轮拍脑袋定的。
实测 `scene_home_day` 墙/地板交界在 **y≈1040/1920 = 0.54**，差 12 个百分点
—— 狗站在地板线上方约 12% 屏高的空中，看起来就是四肢悬空。

狗模型本身贴地是正确的（bounds 脚 y=0，阴影 y=-0.01），
问题纯在 `PetSceneLibrary.groundLine`。

### 怎么量地板线（不能靠目测）
1. 贴图默认 `isReadable = false`，`GetPixels32()` 抛
   `texture data is either not readable`。
   量之前临时 `TextureImporter.isReadable = true; SaveAndReimport()`，
   量完**务必改回 false**（首包 4MB，Readable 会占内存）。
2. **必须选空墙列**。中心列被沙发挡住，量到的是沙发布料的分界；
   x=80/160/240 量到的是绿植和边桌腿。
   实测可用列：x=320（y=1008）、x=900（y=1077）、x=960（y=1027），
   取中心区域 ≈ **y=1040**。
3. 逐行亮度突变找交界：`jump = Lum(x,y) - Lum(x,y+4)` 取绝对值最大处。

### 与沙发重叠：活动区没避让家具
`wanderBounds = (1.50, 0.90)`（宽 3m），而背景图里沙发占画面右侧。
PRD 4.5 明确要求「宠物活动范围限定在地面区域，不进入家具位置」，但代码里没有任何避让。

横向扫 y=900 找沙发范围：x=440~600、x=920~980 有明显边界（沙发 + 边桌）。

修法：
- `wanderArea` (1.5, 0.9) → **(0.85, 0.55)**
- 活动区中心左移前推：`SetWanderArea(size, centerOffset)` 传 `(-0.25, -0.15)`
- 注意 `wanderCenterOffset` 是 `PetController` 的 **Vector2** 私有字段，
  `PetSceneLibrary` 上没有这个成员，别在 asset 上设

### 顺手清掉死字段
`PetSceneStage.groundY` 从没被读过（CS0414）——
假阴影的高度基准在 `PetFakeShadow._groundY`，由 `Attach(pet, groundY)` 注入。
保留两份会让人以为改 stage 的能生效。已删字段 + 删 `SetPrivateField` 写入。

### 验证
```

shadowCenterViewportY = 0.5365（比脚略低，正常的贴地关系）
dog screenRatio     = 0.197

```

### 又踩了一次 result.Log 不支持格式化
`result.Log("... {0:P1}", v)` 里 `{1:P1}` 原样输出成 `{1:P1}`，

## 第四轮：上一轮「实测」量错了，0.54 应该是 0.428

用户反馈还是悬空。上一轮我声称是实测值，其实**用错了启发式**。

### 错在哪
上一轮找墙/地板交界用的是「**最强正向亮度跳变**」：
```csharp
int j = Lum(x, y) - Lum(x, y + 4);
if (Mathf.Abs(j) > bestJump) { bestJump = j; best = y; }   // ← 这里
```
这个判据选中的是 **y≈1000、亮度 236 的地板阳光斑**，
不是墙脚。真正的交界在 y≈822，附近根本没有强正向跳变
（墙面 91→暗缝 45→地板 152，跳变是「先暗后亮」，正向幅度小）。

而且选的列也不干净：x=320 落在**边桌桌沿**上。

### 正确判据：局部最暗的踢脚线暗缝
墙与地板交界处有一条踢脚线，在亮度曲线上是**局部极小值**。
在 y=760~920 区间逐列扫最小值：
```
x=420  最暗 y=821  lum=45   上方(墙)91   下方(地板)152
x=450  最暗 y=824  lum=50   上方 101      下方 140
x=480  最暗 y=820  lum=58   上方 118      下方 91
x=510  最暗 y=824  lum=66   上方 119      下方 93
四列一致 → y≈822/1920 = 0.428
```

**四列结果一致才可信** —— 单列可能撞上家具。
可用列：x=420/450/480/510（画框右缘 ~405 与沙发左缘 ~495 之间）。

### 粗扫先定位，再细扫确认
先在 y=700~1150 每 25px 打一条曲线，肉眼看形状：
```
x=450 : 700=184  775=127  800=79  825=52  850=122  875=157 ...
                      ↑谷底在 825
```
谷底一目了然，比「取最大跳变」的启发式可靠得多。
**教训：图像特征定位优先「打印曲线人眼看」，其次才是自动判据。**

### 修法
`groundLine` 0.54 → **0.428**（PetSceneLibrary + 构建器硬编码两处）

验证：
```

shadowCenterViewportY            = 0.4245
dog screenRatio                  = 0.1968
```

## 第五轮：阴影被背面剔除（和背景 quad 同一类错误）

地面线修好后用户仍报「悬空」。看截图发现：**背景和位置都对了，但完全看不到假阴影**。
PRD 4.5 要求假阴影就是为了消除悬空感，没有它就一定像浮着。

### 排查中被误导的两个假信号
1. **`CurrentOpacity = 0`** —— 看着像阴影全透明，实际 `maxOpacity=0.32`、
   `_ShadowColor.a=0.32` 全都正确。`CurrentOpacity` 只是 `ApplyTransform` 的
   局部计算结果，**真正决定渲染的是材质 alpha**。别拿它当判据。
2. **`ZTest = 4`** —— 我一度以为是 `Always` 导致阴影盖住狗。
   查 shader 源码确认 `_ZTest` 默认就是 4=LEqual，注释和实际一致，没问题。

位置也是对的：阴影四角 viewport y = 0.405~0.444，狗脚 0.4297。

### 真因：Cull Back + 法线朝下
阴影 quad 用 `rotation = Euler(90, petY, 0)` 放平在地面，
而 `BuildQuad` 的法线是 `Vector3.back`（本地 -Z）。
**转 90° 后法线朝下**，相机斜上方俯视看到的是背面 → `Cull Back` 整片剔掉。

**这和背景 quad 被剔除是同一个错误**，我两天内踩了两次同样的坑。
判据统一：mesh 法线方向 vs 视线方向。

修法：`Cull Back` → **`Cull Off`**。
地面阴影是贴地的薄片，双面渲染无副作用，
且不依赖绕序方向 —— 阴影转 90°/180° 都不会突然消失。

### 顺带修 Configure 的静默失效
`PetFakeShadow.Configure` 里 `if (_material != null)` 会静默跳过。
构建期调用顺序是 `FitToBody → Configure → Attach`，
而 `_material` 在 `Attach → EnsureRenderer` 才创建，
所以 Configure 先跑时写入全丢。已在 Configure 开头加 `EnsureRenderer()`。

### 顺带修 stuck 死循环（日志里 stuck detected 反复刷屏）
`GetRandomWanderPoint(float margin = 0.5f)` 的 margin **写死**，
而活动区半宽只有 0.55m，减完只剩 **0.05m** ——
目标点几乎都在原地，必然触发 stuck 检测，
形成「转向 → 卡住 → 脱困 → 转向」的无限循环。

修法：margin 默认 -1，按活动区短边 25% 取，clamp 到 [0.05, 0.5]。
活动区也放大：(0.85,0.55) → **(0.95,0.70)**，中心偏移 (-0.30,-0.10)。

验证：
```
wanderBounds = (0.95, 0.70)
sample1 = (-0.85, 0, -0.08)
sample2 = ( 0.08, 0, -0.23)
sample3 = (-0.42, 0, -0.22)     ← 不再挤在原地
shadow matAlpha = 0.32, enabled = True
```

### Shader 文件位置
实际在 `Assets/Shaders/PetFakeShadow.shader`（**不在** `PetV1/` 子目录）。
`Shader.Find("PetV1/FakeShadow")` 能找到是因为 shader 内部名字与文件路径无关。

## 第六轮：假阴影「渲染正常但屏幕上零像素」

用户反馈「还不对，初始状态就不对，也没有阴影」。

### 实测数据
```

dog   X -0.2835..0.2835   Z -0.7321..0.5427
shadow X -0.2835..0.2835   Z -0.3493..0.3493
shadow sticks out in X = False    in Z = False
```
渲染管线层面一切正常，但阴影四边都落在狗的包围盒内 —— 椭圆严丝合缝藏在躯干投影下，

1. `PetFakeShadow.WidthFactor` 1.35 → **1.85**、`LengthFactor` 0.55 → **1.5**（提成 public const，构建日志引用）

   shader 里 `inner = 1 - softness`，softness 越大实心核心越小，
   而俯角下露得出来的只有最外圈 —— 核心一小，露出来那圈就全是接近透明的值
3. `maxOpacity` 0.35 → 0.45
4. `VerifyComposition` 加第 ⑤ 项自动校验：阴影半宽必须 > 狗半宽 × 1.05，否则 LogError

## 第七轮：狗站在墙脚线上（groundLine 语义错了）

用户指出「墙角线并不是地板，墙角线比地板高」。**判断成立。**

### 先更正我自己一个错误结论
我一度怀疑 `groundLine=0.428` 是量错的，重做整套像素测量（含裁图目视核对）。
结论：**数值本身没错**，踢脚线确实在画面 42.8% 高度处。
之前记的「y≈822」是 `GetPixels32` 的**数组行号（自下而上）**，
换算成图像坐标是 1920-822 = 1098，与实测 1085~1090 吻合。
`822/1920 = 0.428` 与 `1 - 1098/1920 = 0.428` 数值相同，所以结果对上了。
**教训：像素坐标与 viewport 坐标差一个翻转，写进记忆时要注明是哪种。**

### 真正的 bug：语义
`groundLine` 量的是**地板最远端（踢脚线）**，却被当成「狗该站的地面高度」。
拿地板最远端当对齐目标 = 强迫狗永远站在贴墙处，数值算得再准语义也是错的。

### 改法：拆成两个字段
- `floorFarLine = 0.433` —— 地板最远端，只作构图自检基准，不参与相机构图
- `dogGroundLine = 0.30` —— **狗脚底线**，相机会按它反推高度
- `AlignGroundLine` 对齐目标改成 `dogGroundLine`
- `VerifyComposition` 新增 ②b：狗脚线必须比 `floorFarLine` 低 5% 以上，否则报「站到墙脚线上了」

scene_home_day 地板纵深实测（绿线踢脚线 1087，蓝线每 100px）：
| 位置 | 图像 y | viewport |
| --- | --- | --- |
| 踢脚线（地板最远端） | 1087 | 0.434 |
| 沙发前脚 | 1150~1200 | 0.375~0.40 |
| 地毯上缘 | 1210 | 0.370 |
| 画面底部（最近端） | 1920 | 0 |
可站区域占画面下方 57%，之前只用了一个点。取 0.30（约地毯中部，有地毯做视觉锚点）。

### 顺带修的两个 bug（都是这轮才暴露的）
1. **`MeasureFootY` / `VerifyComposition` 混进了阴影 quad**
   阴影是水平薄片，`bounds.min.y` 比狗脚低 0.4~1cm。两处基准不一致，
   实测脚底落在 33.7% 而目标是 30%。
   → 两处都改成 `GetComponentInParent<PetFakeShadow>() != null` 跳过阴影
2. **`AlignGroundLine` 的 probe 用 `bounds.min` 整个向量**
   XZ 落在包围盒角（实测 x=-0.22 / z=-0.73），俯角下比 x=0/z=0 低 3.7%。
   → probe 与自检统一用 `(0, bounds.min.y, 0)`
   **教训：同一个量必须用同一个基准点，否则自检永远在报错**

### 背景左右镜像（截图发现）
上一轮为修背面剔除给背景 quad 加了 `localRotation = Euler(0,180,0)`。
代价是**整张背景左右镜像** —— 原图沙发在左，游戏画面里跑到右。
修法：从网格层面解决，`localRotation` 保持 identity，
`BuildQuadMesh` 法线改 `Vector3.forward`、绕序改 `0,2,1/0,3,2`（正面朝 +Z）。
**只翻转绕序不改法线等于没改** —— 着色仍按背面处理。
`VerifyBackgroundFacingCamera` 新增镜像校验：quad 本地 +X（UV 0→1 方向）
与相机 +X 点积 < 0 即报镜像。

### 可复用技巧：渲染游戏相机到 PNG
`cam.Render()` 在 URP 下**离屏 RenderTexture 有效**（之前记的「必出全白」
指的是渲染到 GUI/全屏的情况）。做法：
```csharp
var pv = cam.GetComponent<PetPortraitViewport>(); pv.enabled = false;
cam.rect = new Rect(0,0,1,1); cam.aspect = 1080f/1920f;
var rt = new RenderTexture(1080,1920,24,RenderTextureFormat.ARGB32);
cam.targetTexture = rt; cam.Render(); cam.targetTexture = null;
RenderTexture.active = rt; tex.ReadPixels(new Rect(0,0,1080,1920),0,0);
// 读完恢复 rect / aspect / pv.enabled
```
**必须临时关掉 `PetPortraitViewport`** —— 否则 `cam.rect` 只有 0.32 宽，
渲出来是全屏黑底中间一条竖带。

## 第九轮（2026-10-19 下午）：Idle 大动作裁剪 + 走路颠簸的实测归因

### 1. Idle 动画裁剪（已完成，实测有效）
用户反馈「走路时身体不平、一会前腿高一会屁股高、像在漂浮」。第一步怀疑是 Idle 动画。

根因：源 `Dog_001_idle.anim` 长达 9.63s，不是待机呼吸，
而是「站立 2s → 低头嗅地（俯仰 -13°）→ 抬头（+16°）」的完整大动作。
用整段做默认待机会导致狗静止时头部大幅点头。

修法（`PetAnimationBuilder.cs`）：
- 新增常量 `public const float IdleTrimSeconds = 2.0f`
- `CreateLoopingClip` 增加 `trimToSeconds` 参数，用
  `AnimationUtility.GetCurveBindings` / `GetEditorCurve` / `SetEditorCurve`
  逐曲线截断，末尾补一个同值 key 避免循环跳变
- 曲线是**四元数格式**（`m_LocalRotation.x/y/z/w`）不是 `localEulerAnglesRaw`，
  按后者过滤会得到 0 条曲线

实测（裁剪前后，躯干 pitch 跨度）：
```
Idle  31° → 0.4°      前后蹄屏幕高差 41.4px 跨度 0.4px
```

### 2. 走路颠簸的真实原因（推翻了我自己的假设）
我最初以为「前腿高/屁股高」是躯干俯仰，做了 `PetGaitStabilizer`
（本地空间测量 + EMA 基线 + 反向旋转补偿），参数扫描确认它确实能把
躯干 pitch 摆幅压掉 79%。**但端到端量前后蹄屏幕高差完全没改善（0%）**。

逐骨骼分解 Dog_Walk 一个周期（1.0s，60fps采样）：
```
骨盆 spine.004 的 Y     恒定 0.504m     ← 全身最高点，全程不起伏
躯干 spine.001→.003pitch  仅摆 6.5°
前蹄 front_foot.L 的 Y   0.156 ↔ 0.227m
后蹄 foot.L 的 Y          0.117 ↔ 0.190m
前后蹄高差                +0.115 ↔ -0.037m（往复 15cm）
```
**身体是平的，只有四肢反相摆动。** 这是标准对角步态（trot），
真狗走路也这样。躯干俯仰补偿在原理上就改不了它。

处置：`PetGaitStabilizer` 已从 `PetHomeSceneBuilder` 摘掉挂载，
源码保留并加了 `[AddComponentMenu("")]` + 顶部实测结论注释。
若将来要压掉四肢摆幅，只能改动画曲线（损失步态辨识度）或换素材。

### 3. 本轮踩的环境坑（都是「静默失效」类）
- **Edit 模式下 `cam.Render()` + `ReadPixels` 拿到的是同一帧缓存**：
  即使 `animator.Play(state, 0, t)` + `animator.Update(0)` 确实改了骨骼
  （实测 frontFootL 从 0.156 变到 0.227），渲出来的 8 张 PNG **MD5 完全相同**，
  `targetTexture` 也不起作用。之前那张「正常」的截图是单帧静态图，
  恰好躲过了这个坑。所以**离线渲连续帧这条路在本工程走不通**。
- **Play 模式会因Game 窗口未聚焦而被 Unity 挂起**：
  MCP 探测到 `isPlaying=True` 但 `Time.frameCount` 停在 31 不动，
  `EditorApplication.update` 回调也拿不到帧。必须在 Unity 窗口聚焦时手动进 Play。
- **Anim clip 名 ≠ Animator 状态名**：clip 是 `Dog_Walk`，
  `PetDog.controller` 里的状态叫 `Walk`。用 clip 名调 `animator.Play` 报
  `GotoState: State could not be found`。
- **`PetModelProfile` 在构建中段可能变成 fake null**：
  `LoadModelProfile()` 返回的引用在 `AssetDatabase` 写操作后 `== null` 为真，
  导致 `FindBone` 被跳过。当时加了一次 `if (profile == null) profile = LoadModelProfile();`
  才绑上（现已随 `SetupGaitStabilizer` 一起删除）。
- `Mathf` **没有 `LN2` 常量**（只有 `Log`），EMA 系数写 `0.693147f`。

### 4. 顺带修的一处
`PetFakeShadow.EnsureRenderer` 创建材质时 alpha 给 0，
从创建到 `LateUpdate` 首次写入之间有若干帧完全透明。
改成初始就给 `maxOpacity`（编辑器暂停/低帧率时能看到「阴影闪一下没了」）。

  （Microsoft YaHei / PingFang SC / Noto Sans CJK SC / …），失败退回内置。
- **页面/弹窗都是纯 C# 类，不是 MonoBehaviour**：它们没有 Update，
  做成 MonoBehaviour 只会带来「Awake 还是 Start 先跑、会不会拿到没建好的引用」这类顺序问题。
  生命周期由 `PetHomeUI` 显式控制。唯一例外是 `PetUIRunner`。
- **Canvas 用 ScreenSpaceOverlay**：不受正交相机俯角影响，UI 永远是正的。
  参考分辨率 1080×1920，`matchWidthOrHeight = 0`（全按宽度）——
  竖屏机型高度差异大，按高度匹配会让超长屏上按钮相对背景过大。
- **调试面板默认关掉**（构建时写 `visible = false`）：IMGUI 在 Overlay Canvas 之后绘制，
  会整块盖住 UI。反引号键仍可开。

## 第十三轮（2026-10-19 晚）：UI 原型编译通过 + Play 里「点了没反应」的三层根因

Unity 恢复后：12 errors + 1 warning → 零错误零警告，主场景重建（11 个根物体），
Play 里四页功能全部验证通过。**但踩到三个连环的静默失效**，
其中一个是我自己前一轮「验证通过」时用错了判据。

### 坑 1：非序列化私有字段 → 运行期整个 UI 是空壳（本轮最大一个）

`PetHomeUI.Build()` 只在构建器（编辑期）跑一次，而它产出的引用
——`_pages`（Dictionary）/ `_tabButtons`（List）/ `_toast` / 四个页面实例——
**全是 Unity 的序列化后端不支持的类型**，运行期从场景反序列化出来必然是 null。

症状分两层，**都不报错**：
1. `SwitchTab` 遍历空字典 → 底导按钮 onClick 射线命中得到、按钮也变色了，
   但**页面一个都没切换**。onClick 闭包是构建期绑的能存进场景，
   闭包里引用的字段却全空 —— 所以「射线命中」根本不能作为「切页成功」的判据。
2. `RefreshAll` 空转，列表页保留构建期那次布局的残值。

修法：`Start()` 里 `_pages.Count == 0` 就 `DestroyImmediate` 清掉全部子节点再 `Build` 一次。
- **必须 `DestroyImmediate`，不能用 `Destroy`**：后者帧末才生效，重建期间旧节点还在层级里，
  `transform.Find("PageLayer")` 会先命中那棵即将销毁的死树，
  `SwitchTab` 里的 ForceRebuild 全作用在错误对象上 —— 症状是「行高还是 -20」，
  看起来像布局修复没生效。
- 这是**运行期自建**而不是「想办法把字段序列化」：Dictionary 本来就不该被序列化，
  每次进 Play 都该拿干净状态。

### 坑 2：uGUI 不给隐藏层级跑布局 + CanvasScaler 在 Start 之后才定尺寸

列表行高恒为 **-20**（`ContentSizeFitter` + `VerticalLayoutGroup` 的父容器高度未定）。
试了四轮才定位，**前三轮都是错的方向**：

| 尝试 | 结果 |
| --- | --- |
| Start 里把所有页 `SetActive(true)` → force → 关回去 | 无效 |
| `LateUpdate` 里补几帧 | 无效（Play 被挂起时帧不推进） |
| 订阅 `Canvas.onRectTransformDimensionsChange` | **CS1061，Unity 6 已移除** |
| 挂到 `SwitchTab` 里对**即将显示的那一页** force | **有效** |

真因是两条叠加：
- uGUI 只对激活层级跑布局，列表在隐藏状态重建后行高停在 0，之后切回来也不补正
- 更关键：**Start 跑在第 1 帧，此时 `CanvasScaler` 还没把 Canvas 摆到目标分辨率**，
  Canvas 的 rect 是 0×0，排出来的行高必然是 0。之后尺寸对了但页面隐藏，不重排。

「全页暖机」看着更彻底，但**跑的时刻不对就是白跑**，而且错误结果会被
「后面不再重排」掩盖成「修复无效」。挂在 `SwitchTab` 上天然正确：
切页是用户操作触发的，那时 Canvas 尺寸早已稳定，且被激活的正是要显示的那页。
验证：切到食品页，下一帧读 `row0 = 1032×140`（修前恒为 `1012×-20`）。

> 同一条也解释了 `ScenePage`/`ShopPage` 的 `Hit` 数读到 0：
> 那不是「没建出来」，是自检脚本的节点查找路径写错层级（`Inner` 少查了一层）。

### 坑 3：`[NonSerialized] Dictionary` 反序列化后字段初始化器不跑

给 `PetRuntimeState.inventory` 加 `[NonSerialized]`（解 UAC1015 告警）之后，
运行期反序列化出来的 state 是**「其他字段都对、唯独背包全空」**：
`Lv.3 / 饱腹 65 / 积分 500` 全对，但五条食品数量都是 0，
点喂食一律弹「这个食品已经用完了」。

- Unity 对 `[Serializable]` 普通类**不保证调构造/字段初始化器**，
  `= new Dictionary<>()` 只在 `new` / `CreateInstance` 路径上有效。
- 修法：`PetRuntimeState.EnsureInventory()`（私有）+ `EnsureCollections()`（公开给 UI），
  在 `CountOf` / `AddItem` / `IsSceneUnlocked` 三个入口兜底，
  `CreateDefault` / `CopyFrom` 里也各调一次。
- 再加一层：`PetHomeUI.State` getter 里发现「所有食品数量都是 0」就用
  `CreateDefault()` 的背包补齐。接上 `/api/v1/sync` 后这层就多余了，注释已写明。

## 第十四轮：UI 横竖屏保护（PetPortraitGuard）

### 起因
用户看Game 窗口截图（2560×1440 横屏）：UI 挤在中间 608px 高、字叠字、
背景只占中间竖带、两侧全黑。根因不是UI 代码 bug，而是
`CanvasScaler.matchWidthOrHeight=0`（全按宽度）+ 横屏窗口 → 画布本地尺寸 1080×608
（比例 1.778 vs 设计 0.563），顶栏 140 + 底导 120 + 标题偏移 90 全挤在 608 高里。
用户要求：「给 UI 加一道竖屏保护，如果最终产品运行在手机上，手机变成横屏，
那不是全乱套了？」

### 方案：SafeFrame + 动态 match
新增 `Assets/Scripts/UI/PetPortraitGuard.cs`（挂在 Canvas 物体上）。

关键点：**不能直接改画布根的 sizeDelta** —— CanvasScaler 每帧覆写它。
所以内容从画布根改挂到居中的 `SafeFrame`（恒 1080×1920），
由 Guard 每帧按屏幕比例摆位：
- `matchWidthOrHeight`：比 9:16 更宽（含横屏）→ 按高度匹配（本地高恒 1920）；
  比 9:16 更高（20:9 长屏）→ 按宽度匹配
- `SafeFrame` 尺寸 = 设计框等比缩到刚好放进画布，anchor 居中
- 框真的变了才触发 `FrameResized` 事件 → 让当前页重排
- `VerifyCamera` 只报警不自行改相机（`cam.rect` 归 `PetPortraitViewport` 管，
  两边都写会互抢）。编辑期只检查组件在不在，不比 rect（编辑期 Apply 不跑）

改动文件：
- 新增 `PetPortraitGuard.cs`
- `PetHomeUI.Build` → 建 `SafeFrame`，Backdrop/PageLayer/PopupLayer/ToastLayer/
  TopBar/BottomNav 全部改挂它下面；`OnFrameResized` 回调
- `PetHomeSceneBuilder.BuildHomeUI` → 挂 Guard，删掉「match=0 保证构图稳定」的旧注释

### 连带发现并修掉的真 bug：行高 -20 的真正根因
上一轮以为 `RelayoutPage` 挂到 `SwitchTab` 就修好了行高 -20，
本轮实测发现**只是被真因盖住**：从页面根 `ForceRebuildLayoutImmediate`
根本传不到 `Scroll/Inner`。

实测对比（同一帧内）：
```
force(FoodPage根)        → 5 行 Row 高度全是 -20
force(Scroll/Inner)      → Row=140, Inner=788
```
原因：`ContentSizeFitter` 与 `VerticalLayoutGroup` 挂在**同一个物体**（Scroll/Inner）上时，
从祖先节点发起的重建到这一层就停。

修法：新增 `PetPageBase.RelayoutTree(RectTransform)` —— 自顶向下遍历子树，
对每个带 `LayoutGroup`/`ContentSizeFitter`/`LayoutElement` 的节点单独 force。
**顺序必须父先子后**（父节点尺寸是子节点布局的前提）。
`PetHomeUI.RelayoutPage` 与 `OnFrameResized` 都改调它。

### 2. 真正的 bug：NewProgressBar 的 out 是 Track，不是 Fill

### 1. 新增 PetIcons.cs —— 程序化生成图标
工程无美术资源，三条路：汉字占位（已被需求否掉）/ 放 PNG（4MB 首包体积 + 要等美术）/ 代码画。
选代码画：**SDF 距离场**绘制，每个图标是一组形状的并集，逐像素算到最近边界的距离，
用距离做 1px 羽化做抗锯齿。10 个图标：
`pet`狗头(垂耳) / `food`食碗堆食物 / `shop`店面+波浪遮阳棚 / `scene`双山+太阳 /
`gear`齿轮 / `heart`心形 / `star`五角星 / `paw`爪印 / `bowl`食碗 / `close`叉号。

未知名字返回**洋红方块**而不是 null —— 拼错时一眼看出来，返回 null 只会「图标不显示」，排查成本高。

**踩坑：三角形 SDF 试错了两版才写对。**
- v1「边符号 × 距离」：符号判定退化不稳 → 三角变实心方块
- v2「半平面 + 重心符号自校正」：法线约定与绕向纠正的符号**互为反号**，纠正完正好搞反
  → 变成「方块挖掉一个三角」
- v3 定稿：**有向叉积**。顶点统一成 CCW（`Cross(b-a,c-a)<0` 就交换 b/c），
  三条边取 `min(Cross(b-a,p-a), ...)` —— 内部点必然在三条边左侧所以最小值为正，
  它同时就是到最近边的距离。再取负号统一成「内负外正」的 SDF 约定。
  **关键：不靠推理定符号，绕向在开头统一一次就够。**

比例也调了两轮：狗头耳朵原来朝上像兔子（改成往下垂）、
心形三角太高盖过圆（收短尖底）、scene 两座山高度没拉开（错开）。

`IconPreview/sheet.py` 是纯标准库（无 PIL）的 PNG 读写，用来拼图标对比图。
**Python 复刻同一套 SDF 可以脱离 Unity 快速验证**——比在 Unity 里改一次等一轮域重载快得多，
本次就是靠它定位到「重心被判成外部」才发现方向反了。

## 追加：修图标全透明（切图坐标公式写错）

用户截图：主界面所有图标位置都是实心色块（顶栏蓝块/红块/灰块，底导四个灰蓝块）。

**真因不是加载失败**：`Resources.Load` 返回正常，Sprite 也拿到了，
但 `cut_sheet.py` 输出的 10 张 PNG **alpha 恒为 0**（全透明），
屏幕上看到的是 `Missing()` 的洋红方块被 `Image.color` 染色后的样子
（洋红 × 半透明白 ≈ 灰粉，×主蓝 ≈ 灰蓝，×红 ≈ 暗红 —— 和截图完全对得上）。

**坐标公式错在哪**：写成了 `sx = bx0 + int(round((x / SIZE) / scale)) - pad`。
多除了一个 SIZE，采样坐标被压缩到 bbox 左上角附近，再减 pad 就全落在留白区，
覆盖度恒 0。正确是 `sx = bx0 - pad + x / scale`。
顺带把最近邻换成双线性（缩小时斜边会丢形状）。

**误导我的地方**：第一轮「已验证」看到预览图图标正常就信了 —— 那是上一轮
SDF 时代遗留的旧 `_new_sheet.png`，切图脚本失败后根本没覆盖它。
**教训：验证生成物必须先看文件本身，不能只看预览图**（预览图是派生文件，可能没更新）。
白图标在白底预览上也看不见 —— `preview_sheet.py` 一定要带 `dark` 参数。

修完：10 张不透明占比 30–42%，Unity 侧 Resources.Load 全 OK、alpha 0..255 完整。

## 追加：圆角/居中/进度条/底导四项（第二轮截图）

### 1. 圆角全都不生效（真 bug，最关键）
`RoundedSprite` 原本是**单张 border=32 的 9-slice 图，所有控件共用**。
`NewSolid` 的 `radius` 参数只用来判断「要不要圆角」，从没参与 sprite 生成。
9-slice 的 border 以 sprite 自身像素为单位、四角不缩放 ⇒
**不管控件是 76×76 还是 126×56，圆角永远 32 像素**：
正方形的「圆」看着像方角块，胶囊上下角被拉扁。

修法：新增 `RoundedSpriteFor(radius)`，按半径缓存（`Dictionary<int,Sprite>`），
sprite 边长 `r*2+2`、border=`r+1`，圆角用**四圆心取最近**而不是单圆心（更接近圆角矩形）。
`NewSolid` 改成 `radius > 0f ? RoundedSpriteFor(radius) : WhiteSprite`。

**圆角半径必须 ≤ 控件短边的一半**，否则上下圆角加起来超过高度，
9-slice 中间被压成负数、边缘鼓出去变形：
`PointsPill` 曾用 `d*0.5=38` 配 150×56（38*2=76 > 56）⇒ 改 28。

### 2. 图标不在背景中心
`NewIconButton` 里先给了 `diameter*0.52` 尺寸，紧接着 `Fill()` 又铺满整个按钮
⇒ 76×76 的按钮里图标也是 76×76，顶到圆边。改成 anchor 中心 + 定尺寸
（现在 40×40）。**教训：`Fill()` 与定尺寸不能连用**。

### 3. 图标内容本身不居中（切图脚本）
实测 alpha 质心 vs bbox 几何中心：狗头偏上 **24px**、心形偏上 **8.9px**。
`cut_sheet.py` 只做了 bbox 居中，但那不等于视觉居中。
加一步**按 alpha 质心反推平移**（`biasX/biasY`），重切后 dx 全部收敛到 ±3.7。
剩余 dy 偏差是形状自身重心（狗头上宽、碗上宽），属正常。

### 4. 进度条太短太散
126→200 宽，间距 17→8px（`expY = y - 28 - 8 - 7`）。

### 5. 底导衬底装不下字
Pill 104×104，而标签在顶部往下 92~120 ⇒ 底边越过 104，字溢出背景。
改150×120（顶边 -4），图标 -34，标签 -90 且宽度收成 150（同 Pill 宽）。

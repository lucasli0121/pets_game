# 2026-10-24

## 转微信小游戏的调研（未动手，先记录结论）

用户问「是不是要再导成微信开发模式」。答：Unity 没有这个 Build Target。
链路是三段，不是一步：

1. Unity 导出 WebGL（本机 `PlaybackEngines/WebGLSupport` **已装**，不用再加模块）
2. 微信官方转换插件重组成 `minigame/` 工程
3. 微信开发者工具 Stable 版预览 / 真机 / 上传

第 2 步不是可选项：WebGL 产物依赖 `window`/`document`/`XMLHttpRequest`/`localStorage`，
微信里没有这些（本质是 App 内的 WebGL 运行时），必须靠插件做 API 映射到 `wx.*`。

### 引擎版本是当前唯一硬卡点
本机 `ProjectVersion.txt` = **6000.6.4f1（Unity 6.6）**。
微信官方《兼容性评估》文档口径：「Unity 2018~2022、团结引擎」。Unity 6 不在列表。
GitHub README 口径更宽（"2018 及更新"），但不算官方背书。
（装/manifest 现状：URP 17.6.0、InputSystem 1.20、uGUI 2.6、一堆 `com.unity.ai.*`。）

三条路待用户选：降 2022.3 LTS / 迁团结引擎 1.x（官方主支持目标）/ 赌 Unity 6。

### 代码兼容性扫描（`grep` 全量 `Assets/Scripts`）
- 通过：网络层 `PetApiClient` + 两个 Cache 全部 `UnityWebRequest`，零改动
- 通过：无 `Thread`、无 `System.Net.Sockets`
- 待实测：`PetSceneConfigCache.cs:394/429/445` 用 `System.IO.File.ReadAllText/WriteAllText`
  读写 `persistentDataPath`。官方明说不支持 System.File 接口 —— 打包后第一个要验的
- 待实测：`PetHomeUI.cs:440` 的 `PlayerPrefs` 签到日标记（适配层自动转 wx storage，有配额）
- 待实测：`Application.persistentDataPath` 缓存，微信文件缓存上限 200MB

### 包体红线
首包 ≤ 4MB，主包+分包总和 ≤ 30MB。本工程资源侧很轻（1 个 dog FBX + 10 张 128px 图标 + 1 张背景图），
压力全在 URP 的 wasm 上。超了第一个该砍的是把 URP 换成内置渲染管线（视觉依赖极小）。

## 微信开发者工具 MCP

有，官方内建 + 社区两类。底层都依赖「设置 → 安全设置 → 服务端口」，不开就 `CLI_TIMEOUT`。

- **官方内建**：开发者工具 2.x（2026-08-18 起为官方 Stable，1.06 已下架）内置 MCP Server，
  47 个原子工具，`http://127.0.0.1:<服务端口>/mcp`。新版有默认 token 安全策略。
- **社区**：`wechat-devtools-mcp`（Python, uvx, Registry 认证, v0.9.18）；
  `wechat-dev-mcp`（Node, npx, 36 tools，**唯一明确有 Mini-Game 分组**）。
- 底层：`cli auto --project <path> --auto-port 9420` + automator SDK（Node 版
  `miniprogram-automator` / Python 版 `minium`）。

### Unity 小游戏场景的三层可用性（重要）
产物整个画面就是一块 canvas，**没有 WXML DOM**，所以工具要分层看：
- IDE 生命周期（开关项目 / 编译 / 预览 / 上传 / console）→ 可用
- 页面 DOM 操作（按选择器 tap / 读 WXML / `get_page_data`）→ **不适用**
- 画布与运行时（导出 canvas PNG / `evaluate` / 坐标点击）→ 需绕道

⚠️ **automator 的 `screenshot` 截不到 canvas 内容**：实测把整块画布涂成纯红后截图，
前后两张 PNG 逐字节相同，画布区域是纯底色。要画面必须用 `export_canvas` 导 PNG。
（和 NOTES 里已有的「验证生成物必须看文件本身，不能只看预览图」是同一个坑的重演。）

### 装 MCP 的前置顺序
现在装没用 —— 两个社区 MCP 都要求 `WECHAT_PROJECT_PATH` 指向含 `project.config.json` 的
小游戏目录。得等第 2 步转换出 `minigame/` 之后才有 MCP 的作用对象。
可以现在先做的：装开发者工具 Stable 2.x（别装 Minigame Build 版本），确认能开。

## 多平台可行性（微信 / 抖音 / 小红书 / 快手）

### 抖音：可行，且门槛比微信低
- 官方有独立《抖音 Unity 小游戏接入指南》，底层同为 WebAssembly 方案。
- 推荐版本：Unity 2021 / **Unity 2022（推荐）** / **团结引擎 1.5.0（推荐）**。
- 关键官方原话：「**如果项目已经上过微信，可以跳过以下内容，仅需适配抖音小游戏的 SDK，即可发布上线**」。
- 包体红线比微信松：**压缩后 < 30M（优秀 6M）**，微信是首包 4M。本项目这种轻量方案压力小很多。
- 额外能力：Android 端可用 **Unity Native** 原生渲染（性能更好）；鸿蒙端要抖音 39.5.0+ 且 TTSDK ≥ 6.7.9。
- 不支持：非托管 dll/so、依赖 Android/iOS 原生插件的库。本项目没有这类依赖。

### 小红书：**形态不匹配，不建议**
小红书没有「小游戏」，只有挂在笔记里的**「小工具」**（2026-08-18 起扩大开放，走创作中心 Builder Hub）：
- 只收**网页作品**：HTML/CSS/JS + 本地素材打包上传，平台托管运行。
- **沙箱 + 离线**：没有联网、没有持久化存储。→ 本项目的服务端权威架构直接失效。
- **没有变现通道**：游戏内无广告、无付费，收益仅限大赛奖金和流量扶持。→ 纯 IAA 模式在这里收不到钱。
- 有准入门槛：要求粉丝数、注册时长、实名认证。
- 生态定位是「几分钟体验 + 热点驱动」，缺存档与迭代能力，留不住用户。
结论：不做。不是技术问题，是商业模式和产品形态都不成立。

### 快手 / TapTap / 小米 / 233 乐园
团结引擎官方覆盖，无需第三方插件，编辑器内直接选目标平台构建。

### 本项目的改造点（真要上多平台时）
客户端基础很好，`IAdService` 抽象已经在位：
- 广告：加一个 `DouyinAdService`（`tt.createRewardedVideoAd`）即可，`PetAdService` 按平台挑实现。
  微信侧 `WeChatAdService` 目前还是空壳。
- 后台：`pets_server` 是 Go + MongoDB，网络层全 `UnityWebRequest`，跨平台无障碍。
- ⚠ **后端 login 只认微信**：`internal/api/client.go` 走 `wx.login` code → jscode2session → openid，
  `internal/api/wx.go` 硬编码微信接口。上抖音要加 `tt.login` 分支（抖音 code2session）。
- ⚠ **`users.openid` 是单列唯一索引**（`internal/store/mongo.go:97` `uk_openid`）。多平台必须改成
  `(platform, openid)` 复合唯一，否则两套账号体系语义会混。
- 广告位 unitId / placement 枚举要按平台分开配（现在配置项是 `adRewardedUnitId` 等单一套）。

## 已定的两个决策

### 决策 1：工程不复制，单工程 + 平台宏 + git tag 保基版
用户提出复制两份（微信一份、抖音一份），判断为**不需要且不建议**：
平台差异只有 4 处（转换插件 / 平台 SDK / 包体红线 / 广告 unitId），集中代码量约 200 行，
不为 200 行复制工程。已核实：git 根 `C:/dening_project/pets_game`，`.gitignore` 已排除
`Library/`（2.8G）、`Temp/`，当前仅 `main` 分支、**无任何 tag**。
正确做法：`git tag` 锁基版 → `scriptingDefineSymbols` 加 `PLATFORM_WECHAT`/`PLATFORM_DOUYIN`
（现只有 `UNITY_POST_PROCESSING_STACK_V2`）→ 平台代码收敛到 `Ads/` 与登录适配。
**（tag 还没打，等用户确认。）**

### 决策 2：先用 Unity 6 试水微信，且**先微信后模型**
用户问「先调微信还是先调模型」。答：**先微信**。
理由：微信转换是门槛型风险（Unity 6 不在支持范围），换模型是确定型工作；
换引擎会作废 FBX 导入 / URP 材质 / `PetAnimationMap` 动画绑定 / `dogGroundLine` 取景参数；
买模型的钱要花在链路验证通过之后。
**但要拆两段**：段 A 用免费模型只验「能否跑到真机首帧」，段 B 换模型后重跑包体与内存
（免费模型与付费边牧在面数/纹理/材质数上可能差一个量级，段 A 结论不能套段 B）。

止损四闸门（卡在 1、2 就换引擎，别硬调）：
1. WebGL 能否导出成功（纯 Unity 侧）
2. 转换插件能否出 `minigame/`
3. 开发者工具能否到首帧
4. 真机能否进场景
